## 2025-11-15: HIGH-008 - 過濾器中的內存洩漏風險

### 問題描述

`FilterType_space()` 和 `FilterType_waterLevel()` 函數在每次執行時會分配大量臨時切片和 map，但缺少重用機制。在 cron 模式下長期運行時，會造成內存逐漸累積，最終可能導致 OOM（Out Of Memory）問題。

**核心問題**：
- **常見誤解**：「Go 有 GC，不用管內存，會自動回收」
- **實際情況**：GC 只能回收**不再使用**的內存，無法解決**內存使用效率低下**和 **GC 壓力過大**的問題

### 影響範圍

- **嚴重程度**: 🟠 High
- **問題類別**: 內存效率、GC 壓力
- **受影響檔案**:
  - `/es-curator/job/filters.go`

### 修復內容

#### 修復的函數

**filters.go** (2 處主要修復 + 新增對象池):

1. 新增 `sync.Pool` 定義（package 級別）
2. `FilterType_space()` - 實施對象池重用機制
3. `FilterType_waterLevel()` - 實施對象池重用機制

```go
    // stringSlicePool 用於重用字符串切片
    stringSlicePool = sync.Pool{
        New: func() interface{} {
            // 預分配 2000 容量，適用於大型 ES 集群

        },
```

```go
func FilterType_space(patternlist []string, disk_space int) (indiceslist []string) {
    // ✅ HIGH-008 修復: 從池中獲取切片，減少內存分配
    creationDateSlicePtr := stringSlicePool.Get().(*[]string)
    indexSortbycreationPtr := stringSlicePool.Get().(*[]string)
    indexSortbycreationAscPtr := stringSlicePool.Get().(*[]string)
    aggregateBytesPtr := stringSlicePool.Get().(*[]string)
    finalIndexListPtr := stringSlicePool.Get().(*[]string)

    indexSizemapPtr := mapPool.Get().(*map[string]string)
    creationdateNameMapPtr := mapPool.Get().(*map[string]string)

    // ✅ 確保歸還給池
    defer func() {
        // 清空切片但保留容量
        *creationDateSlicePtr = (*creationDateSlicePtr)[:0]
        *indexSortbycreationPtr = (*indexSortbycreationPtr)[:0]
        *indexSortbycreationAscPtr = (*indexSortbycreationAscPtr)[:0]
        *aggregateBytesPtr = (*aggregateBytesPtr)[:0]
        *finalIndexListPtr = (*finalIndexListPtr)[:0]

        // ✅ 明確清理 map 後歸還

            delete(*indexSizemapPtr, k)

        for k := range *creationdateNameMapPtr {
            delete(*creationdateNameMapPtr, k)

        stringSlicePool.Put(indexSortbycreationPtr)
        stringSlicePool.Put(indexSortbycreationAscPtr)
        stringSlicePool.Put(aggregateBytesPtr)
        stringSlicePool.Put(finalIndexListPtr)
        mapPool.Put(indexSizemapPtr)
        mapPool.Put(creationdateNameMapPtr)

    creationDateSlice := *creationDateSlicePtr
    indexSortbycreation := *indexSortbycreationPtr
    indexSortbycreationAsc := *indexSortbycreationAscPtr

    finalIndexList := *finalIndexListPtr
```

### 技術細節

#### 關鍵修復點

1. **sync.Pool 實施**:

   - 創建兩個全局對象池：`stringSlicePool` 和 `mapPool`
   - 預分配容量 2000（適用於大型 ES 集群）
   - 使用指針存儲對象，避免值拷貝開銷

2. **對象重用機制**:

   - 使用 `defer` 確保對象一定歸還給池
   - 清空切片時使用 `[:0]` 保留容量（避免重新分配底層數組）
   - map 使用 `delete()` 明確清理所有鍵值對（避免內存洩漏）

3. **返回值處理**:

   - 創建結果副本避免返回池中的切片
   - 使用 `copy()` 確保數據安全性
   - 原始切片在 defer 中歸還給池

4. **內存預分配**:

   - 所有切片預分配 2000 容量
   - 避免 append 觸發多次擴容
   - 減少內存碎片化

### 為什麼 GC 不是萬能的？

#### GC 能做到的：
- ✅ 回收不再使用的對象
- ✅ 自動管理內存生命週期
- ✅ 避免手動 malloc/free 錯誤

#### GC 無法解決的：
- ❌ **頻繁分配**：每次都分配新對象，GC 負擔過重
- ❌ **內存碎片化**：大量小對象分配導致碎片
- ❌ **GC 壓力**：掃描大量臨時對象消耗 CPU
- ❌ **STW 暫停**：GC 時應用暫停（影響響應時間）

#### 開發者的責任：
- 🎯 **減少分配次數**：使用對象池重用
- 🎯 **預分配容量**：避免多次擴容
- 🎯 **明確清理**：歸還前清空 map/slice
- 🎯 **控制生命週期**：及時釋放大對象

#### 實際案例對比

**修復前（依賴 GC）**:

**使用的 Intersection1 實現** (已存在於代碼中):

```go
func Intersection1(a, b []string) []string {
    m := make(map[string]bool)
    for _, item := range a {      // O(n)
        m[item] = true
    }
    var intersection []string
    for _, item := range b {      // O(m)
        if m[item] {              // O(1) hash 查找
            intersection = append(intersection, item)
        }
    }
    return intersection
}
```

### 修復要點

#### 關鍵改進

1. **使用 Hash Map**: 利用 Go map 的 O(1) 查找特性
2. **降低時間複雜度**: 從 O(n²) 降至 O(n + m)
3. **保留備份**: 創建 `Indicesmapping2_bak` 以防需要回退
4. **重用現有代碼**: 利用已存在的高效 `Intersection1` 實現

#### 技術細節

**為什麼 hash map 更高效？**

- 雙層循環需要 n × m 次比較
- Hash map 只需要 n 次插入 + m 次查找
- Hash 查找的時間複雜度是 O(1)

**行為一致性**:

- 原實現可能產生重複元素
- 新實現自動去重（通過 hash map 特性）
- 代碼中已使用 `RemoveDuplicates()` 處理結果，所以去重是期望行為

**備份策略**:

- 保留 `Indicesmapping2_bak` 原始實現
- 如發現邏輯問題可快速回退
- 僅需要將調用改回 `Indicesmapping2_bak`

## 2025-11-05: HIGH-007 - 修復指標中的競態條件

### 問題描述

在 `RecordOperation()` 函數中，對 `opStats.AvgTime` 的讀取和寫入操作存在數據競態條件。雖然使用原子操作更新 `Total` 和 `TotalTime`，但計算和寫入平均時間時沒有同步保護，導致並發訪問時可能出現數據損壞。

### 影響範圍

- **嚴重程度**: 🟠 High
- **問題類別**: 並發安全
- **受影響檔案**:

### 修復內容

#### 修復的函數

**metrics.go** (1 處):

- `RecordOperation()` - 記錄操作指標

#### 問題分析

**競態條件場景**:

1. **非原子讀取**: 第 144-145 行讀取 `opStats.Total` 和 `opStats.TotalTime` 時沒有使用原子操作
2. **非原子寫入**: 第 145 行寫入 `opStats.AvgTime` (float64) 不是原子操作
3. **並發問題**: 多個 goroutine 同時調用時可能：
   - 讀到不一致的 Total 和 TotalTime
   - 同時寫入 AvgTime 導致數據損壞

**實際影響示例**:

```

Goroutine 2: Total=101, TotalTime=5100 → 準備寫入 AvgTime=50.5

併發執行時：
- G1 可能讀到 Total=100, TotalTime=5100 (不一致) → AvgTime=51 ❌
```

#### 修復前代碼

```go
if success {
    atomic.AddInt64(&opStats.Success, 1)
} else {
    atomic.AddInt64(&opStats.Failed, 1)
}

// ❌ 問題：非原子讀取和寫入
```

#### 修復後代碼

```go
atomic.AddInt64(&opStats.TotalTime, duration.Nanoseconds()/1e6)

    atomic.AddInt64(&opStats.Success, 1)
} else {
    atomic.AddInt64(&opStats.Failed, 1)
}

// ✅ 修復：使用互斥鎖保護非原子操作
```

## 2025-11-05: CRIT-004 - 移除重複的 Defer

### 問題描述

在 `CatNodes()` 函數中存在重複的 `defer res.Body.Close()` 語句，這會導致嘗試兩次關閉同一個資源，可能引發運行時 panic。

### 影響範圍

- **嚴重程度**: 🔴 Critical
- **受影響檔案**:
  - `/es-curator/job/nodes.go`

### 修復內容

#### nodes.go 中的 CatNodes() 函數

**問題位置**:

- 第 46 行：第一個 `defer res.Body.Close()`
- 第 51 行：第二個 `defer res.Body.Close()`（重複，已移除）

```go
// 修復後
```

## 2025-11-12: CRITICAL - 修復服務運行時崩潰 (Nil Pointer Dereference)

### 問題描述

當 Elasticsearch 在服務運行期間變得不可用時，服務會因為 nil pointer dereference 而崩潰，並且無法自動恢復。這是一個**生產環境中的關鍵性 bug**，會導致服務完全終止。

### 發現過程

用戶在實際測試中發現此問題：

1. 啟動時 ES 可用且連接成功
2. 排程初始化成功，action 執行及監控數據正常寫入
3. 停止 elasticsearch 服務模擬運行中 ES 短暫斷開
4. 下一次排程時連接不上 ES，**housekeeping 服務崩潰** 💥
5. 重啟 ES 後，housekeeping 服務沒有恢復

### 影響範圍

- **嚴重程度**: 🔴🔴🔴 **CRITICAL - 服務終止**
- **問題類別**: 運行時崩潰、空指針解引用
- **受影響檔案**:
  - `/es-curator/job/indices.go` - ResponseStatusCheck 函數
  - `/es-curator/job/nodes.go` - 3 處調用點
  - `/es-curator/job/shard.go` - 3 處調用點
  - `/es-curator/job/indices.go` - 7 處調用點

#### 根本原因分析

**Bug 模式**:

```go

res, err := req.Do(ctx, es)
// res == nil, err != nil (connection refused, timeout, etc.)
```

#### 為什麼原始代碼沒有 return?

可能的原因：

1. **誤解 error handling**: 以為記錄錯誤就足夠
2. **複製貼上錯誤**: 從其他地方複製代碼時遺漏了 return
3. **缺少 linting**: 沒有使用 `errcheck` 或類似工具檢測

#### Go error handling 最佳實踐

```go
// ✅ 正確模式
if err != nil {
    // 記錄錯誤
    logger.Error("Operation failed", err)
    // 提前返回或返回錯誤
    return nil, err
}

// ❌ 錯誤模式
if err != nil {
    logger.Error("Operation failed", err)
    // 沒有 return，繼續執行！
}
// 這裡可能使用 nil 值導致 panic
```

```go
// initESClientWithRetry 使用指數退避策略重試連接 ES
func initESClientWithRetry() error {
    maxRetries := 5
    if global.EnvConfig.ES.MaxRetries > 0 {
        maxRetries = global.EnvConfig.ES.MaxRetries
    }

    var lastErr error
    for i := 0; i < maxRetries; i++ {
        if err := job.SetElkClient(); err == nil {
            return nil // 連接成功
        } else {
            lastErr = err
        }

        if i < maxRetries-1 {
            // 指數退避: 1s, 2s, 4s, 8s, 16s
            backoff := time.Duration(1<<uint(i)) * time.Second
            global.Logger.Warnw("ES 連接失敗，正在重試",
                "attempt", i+1,
                "max_retries", maxRetries,
                "retry_after", backoff.String(),
                "error", lastErr)
            time.Sleep(backoff)
        }
    }

    // 所有重試都失敗
    global.Logger.Errorw("ES 連接失敗，已達最大重試次數",
        "max_retries", maxRetries,
        "last_error", lastErr)
    return lastErr
}

// 初始化 Elasticsearch 客戶端（帶重試機制）
if err := initESClientWithRetry(); err != nil {
    global.Logger.Error("ES 連接失敗，啟動降級模式", "error", err)
    global.Stderr_logger.Warn("⚠️  服務以降級模式啟動，將定期嘗試重新連接 ES")
    // ✅ 不終止服務，繼續啟動
} else {
    global.Logger.Info("✅ ES 客戶端初始化成功")
}
```

### 重試策略詳解

#### 指數退避 (Exponential Backoff)

**為什麼使用指數退避？**

1. **避免網絡風暴**: 線性重試可能加重故障系統負擔
2. **給系統恢復時間**: 逐漸增加間隔允許 ES 完成啟動
3. **業界最佳實踐**: AWS, Google Cloud, Kubernetes 都使用此策略

**重試時間表**:

```
嘗試 1: 立即連接         → 失敗 → 等待 1 秒
嘗試 2: 1 秒後重試       → 失敗 → 等待 2 秒
嘗試 3: 3 秒後重試       → 失敗 → 等待 4 秒
嘗試 4: 7 秒後重試       → 失敗 → 等待 8 秒
嘗試 5: 15 秒後重試      → 失敗 → 等待 16 秒
最終: 31 秒後放棄，進入降級模式
```

#### 降級模式 (Degraded Mode)

**什麼是降級模式？**

- 服務繼續運行但 ES 客戶端未初始化
- 記錄詳細錯誤信息供調試
- 後續 ES 操作會失敗但不會終止服務
- 配合運行時重連機制，ES 恢復後可自動重新連接

**降級模式行為**:

```
啟動時:
✅ 配置加載成功
✅ 日誌系統初始化
✅ 指標收集器啟動
❌ ES 客戶端初始化失敗（但不終止）
⚠️  進入降級模式
✅ 排程系統啟動
✅ 健康監控 goroutine 啟動

運行中:
- ES 操作記錄錯誤但不崩潰
- 定期嘗試重新連接（透過健康檢查）
- ES 恢復後自動恢復正常運作
```

### 技術細節

#### 為什麼 2^n 指數？

```go
backoff := time.Duration(1<<uint(i)) * time.Second
```

- `1 << uint(0)` = 1 (二進制左移 0 位) = 1 秒
- `1 << uint(1)` = 2 (二進制左移 1 位) = 2 秒
- `1 << uint(2)` = 4 (二進制左移 2 位) = 4 秒
- `1 << uint(3)` = 8 (二進制左移 3 位) = 8 秒
- `1 << uint(4)` = 16 (二進制左移 4 位) = 16 秒

**優勢**:

- 簡潔高效（位運算比數學運算快）
- 間隔增長快速但不會太激進
- 符合業界標準 (HTTP 429 Retry-After)

#### 為什麼選擇 5 次重試？

```
重試次數 | 總等待時間 | 適用場景
--------|-----------|----------
3 次    | ~7 秒     | 網絡抖動、DNS 延遲
5 次    | ~31 秒    | ES 容器啟動、小規模集群重啟 ✅ (推薦)
7 次    | ~127 秒   | 大型 ES 集群啟動
10 次   | ~1023 秒  | 過於激進，不建議
```

**5 次重試是平衡點**:

- 足夠處理大多數暫時性故障
- 不會讓啟動流程等待過久
- 與 Kubernetes 的 readinessProbe 預設值相符

```go
// 最終失敗時
```

## 2025-11-14: NEW-HIGH-001 - Goroutine Panic Recovery

### 問題描述

背景監控 goroutine (`CatCluster`) 缺少 panic recovery 機制，當發生 runtime panic（如 nil pointer dereference、slice out of bounds 等）時，整個監控 goroutine 會終止，導致集群健康監控功能永久失效。

### 影響範圍

- **嚴重程度**: 🟠 High
- **問題類別**: 服務穩定性、錯誤處理
- **受影響檔案**:
  - `/es-curator/job/cat_cluster.go`

### 修復內容

#### 關鍵概念說明

**為什麼需要 Panic Recovery？**

許多開發者誤以為只有明確調用 `panic()` 才需要 panic recovery，但實際上 **Go runtime 會在多種情況下自動觸發 panic**：

1. **Nil Pointer Dereference** (空指針解引用)
   
   ```go
   var node *NodeInfo = nil
   node.Name  // ❌ panic: invalid memory address
   ```

2. **Array/Slice Out of Bounds** (數組越界)
   
   ```go
   arr := []string{"a", "b"}
   arr[5]  // ❌ panic: index out of range
   ```

3. **Map Concurrent Read/Write** (Map 併發讀寫)
   
   ```go
   // Goroutine 1: map[key] = value
   // Goroutine 2: _ = map[key]
   // ❌ panic: concurrent map read and map write
   ```

4. **Send on Closed Channel** (向已關閉的 Channel 發送)
   
   ```go
   close(ch)
   ch <- value  // ❌ panic: send on closed channel
   ```

5. **Type Assertion Failure** (類型斷言失敗)
   
   ```go
   var x interface{} = "string"
   num := x.(int)  // ❌ panic: interface conversion
   ```

6. **Integer Divide by Zero** (整數除以零)
   
   ```go
   count := 0
   result := 100 / count  // ❌ panic: integer divide by zero
   ```

**Background Goroutine 的特殊性**：

- Main goroutine panic → 整個程序崩潰
- Background goroutine panic → **只有該 goroutine 終止**，主程序繼續運行
- 結果：監控功能靜默失效，沒有錯誤日誌，難以排查

#### cat_cluster.go 中的風險代碼

**潛在 panic 場景**：

```go
// 場景 1: API 返回 nil 導致空指針解引用
clusterHealth := ClusterHealth()  // 可能返回 nil
allocations := CatAllocationAPI()  // 可能返回 nil
for _, allocation := range allocations {
    shardCount, err := strconv.Atoi(allocation.Shards)  // allocation.Shards 可能為空字符串或無效
}

// 場景 2: Slice/Map 操作越界
```

### 技術細節

#### Defer 執行順序 (LIFO)

```go
go func() {
    defer fmt.Println("A")  // 最後執行
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Recovered:", r)  // 第二執行
        }
    }()
    defer fmt.Println("B")  // 第一執行

    panic("error!")
}()

// 輸出順序：
// B
// Recovered: error!
// A
```

**為什麼 recover 要最先 defer？**

- 如果其他 defer 在 recover 之前，它們在 panic 發生時依然會執行
- 但如果 panic 未被恢復，程序會在所有 defer 執行後崩潰
- 最先 defer 的 recover 可以確保在其他清理邏輯之前捕獲 panic

#### Recover 的限制

**Recover 只在當前 goroutine 有效**:

```go
func main() {
    defer recover()  // ❌ 無法捕獲子 goroutine 的 panic

    go func() {
        panic("error")  // 這個 panic 不會被上面的 recover 捕獲
    }()
}
```

**每個 goroutine 都需要自己的 recover**:

```go
func main() {
    go func() {
        defer recover()  // ✅ 這個可以捕獲本 goroutine 的 panic
        panic("error")
    }()
}
```

```go
func validateFilters(actionIndex int, action structs.Actiond) error {
    hasAge := false
    hasSpace := false
    hasWaterLevel := false
    hasPattern := false

    for j, filter := range action.Filters {
        switch filter.Filtertype {
        case "age":
            hasAge = true

            // 驗證 direction 有效性
            if filter.Direction != "older" && filter.Direction != "younger" && filter.Direction != "range" {
                return fmt.Errorf("action[%d].filters[%d]: age filter 的 direction 必須是 'older', 'younger' 或 'range'，當前值: '%s'", actionIndex, j, filter.Direction)
            }

            // range 模式的特殊驗證
            if filter.Direction == "range" {
                // range 模式需要 range_from 和 range_to
                if filter.RangeFrom <= 0 {
                    return fmt.Errorf("action[%d].filters[%d]: direction='range' 時，range_from 必須 > 0，當前值: %d", actionIndex, j, filter.RangeFrom)
                }
                if filter.RangeTo <= 0 {
                    return fmt.Errorf("action[%d].filters[%d]: direction='range' 時，range_to 必須 > 0，當前值: %d", actionIndex, j, filter.RangeTo)
                }
                // range_from 是起始時間（較遠），range_to 是結束時間（較近）
                // 例如：range_from=20 (20天前) 到 range_to=1 (1天前)
                if filter.RangeFrom <= filter.RangeTo {
                    return fmt.Errorf("action[%d].filters[%d]: range_from (%d) 必須 > range_to (%d)，因為 range_from 是較遠的過去時間點", actionIndex, j, filter.RangeFrom, filter.RangeTo)
                }
            } else {
                // older/younger 模式需要 unit_count
                if filter.UnitCount <= 0 {
                    return fmt.Errorf("action[%d].filters[%d]: direction='%s' 時，unit_count 必須 > 0，當前值: %d", actionIndex, j, filter.Direction, filter.UnitCount)
                }
            }

            // 驗證 unit 有效性
            validUnits := map[string]bool{
                "seconds": true,
                "minutes": true,
                "hours":   true,
                "days":    true,
                "weeks":   true,
                "months":  true,
                "years":   true, // 支持 years
            }
            if !validUnits[filter.Unit] {
                return fmt.Errorf("action[%d].filters[%d]: age filter 的 unit 無效 '%s'，有效值: seconds, minutes, hours, days, weeks, months, years", actionIndex, j, filter.Unit)
            }

        case "space":
            hasSpace = true
            if filter.DiskSpace <= 0 {
                return fmt.Errorf("action[%d].filters[%d]: space filter 的 disk_space 必須 > 0，當前值: %d", actionIndex, j, filter.DiskSpace)
            }

        case "water_level":
            hasWaterLevel = true
            // water_level 使用 UpperLimit 存儲閾值
            if filter.UpperLimit <= 0 || filter.UpperLimit > 100 {
                return fmt.Errorf("action[%d].filters[%d]: water_level 的 upper_limit 必須在 1-100 之間，當前值: %d", actionIndex, j, filter.UpperLimit)
            }

        case "pattern":
            hasPattern = true
            if len(filter.Value) == 0 {
                return fmt.Errorf("action[%d].filters[%d]: pattern filter 的 value 不能為空", actionIndex, j)
            }
            // 驗證 kind 有效性
            validKinds := map[string]bool{
                "prefix": true,
                "suffix": true,
                "regex":  true,
            }
            if filter.Kind != "" && !validKinds[filter.Kind] {
                return fmt.Errorf("action[%d].filters[%d]: pattern filter 的 kind 無效 '%s'，有效值: prefix, suffix, regex", actionIndex, j, filter.Kind)
            }

        case "node_role":
            // node_role 驗證
            if len(filter.Value) == 0 {
                return fmt.Errorf("action[%d].filters[%d]: node_role filter 的 value 不能為空", actionIndex, j)
            }
            validRoles := map[string]bool{
                "h": true, // hot
                "w": true, // warm
                "c": true, // cold
            }
            // 驗證每個角色值
            for _, role := range filter.Value {
                if !validRoles[role] {
                    return fmt.Errorf("action[%d].filters[%d]: node_role filter 的 value 無效 '%s'，有效值: h (hot), w (warm), c (cold)", actionIndex, j, role)
                }
            }

        default:
            return fmt.Errorf("action[%d].filters[%d]: 未知的 filtertype '%s'", actionIndex, j, filter.Filtertype)
        }
    }

    // 檢查互斥過濾器
    if hasAge && hasSpace {
        return fmt.Errorf("action[%d]: age 和 space 過濾器不能同時使用", actionIndex)
    }
    if hasAge && hasWaterLevel {
        return fmt.Errorf("action[%d]: age 和 water_level 過濾器不能同時使用", actionIndex)
    }
    if hasSpace && hasWaterLevel {
        return fmt.Errorf("action[%d]: space 和 water_level 過濾器不能同時使用", actionIndex)
    }

    // 非 rollover action 建議有 pattern 過濾器（安全措施）
    if action.Action != "rollover" && !hasPattern {
        if global.Logger != nil {
            global.Logger.Warnw("⚠️  建議為所有非 rollover action 添加 pattern 過濾器以避免意外操作系統索引",
                "action_index", actionIndex,
                "action_type", action.Action)
        }
    }

    return nil
}

// getValidActionTypes 取得有效的 action 類型列表
func getValidActionTypes(m map[string]bool) []string {
    keys := make([]string, 0, len(m))
    for k := range m {
        keys = append(keys, k)
    }
    return keys
}
```

### 影響評估

#### 正面影響

1. **Fail Fast 原則**: 啟動時立即發現配置錯誤，避免運行時失敗
2. **錯誤訊息明確**: 精確指出問題位置（action[0].filters[1]）和錯誤類型
3. **防止無效配置**:
   - URL 格式錯誤 → 啟動失敗
   - 帳號密碼為空 → 啟動失敗
   - 過濾器衝突 → 啟動失敗
   - 數值越界 → 啟動失敗
4. **安全性提升**:
   - 強制帳號密碼非空
   - 建議使用 pattern filter 避免誤刪系統索引
   - 過濾器互斥檢查防止邏輯錯誤
5. **維護性提升**: 新增 action/filter 時，驗證邏輯集中管理

#### 需要注意的風險

1. **向後兼容性**:
   
   - 舊配置可能因新驗證規則而啟動失敗
   - **建議**: 升級前先用新版本測試配置

2. **驗證遺漏**:
   
   - 可能仍有未覆蓋的邊界條件
   - **緩解**: 持續完善驗證規則

3. **錯誤處理**:
   
   - 驗證失敗立即退出，無降級選項
   - **理由**: 配置錯誤應在啟動時修正，而非運行時容錯

### 技術細節

#### 關鍵修復點

1. **struct 欄位名稱**:
   
   - `filter.FilterType` → `filter.Filtertype` (小寫 t)
   - `filter.WaterLevel` → `filter.UpperLimit` (water_level 使用 upper_limit 欄位)

2. **切片類型處理**:
   
   - `filter.Value` 是 `[]string`，不能直接比較 `== ""`
   - 使用 `len(filter.Value) == 0` 檢查空值
   - node_role 驗證需要遍歷所有值

3. **驗證順序**:
   
   - ES 配置 → 日誌配置 → 服務配置 → Action 配置
   - 按依賴順序驗證，確保錯誤訊息有意義

4. **錯誤格式化**:
   
   - 使用 `fmt.Errorf("前綴: %w", err)` 包裝錯誤，保留錯誤鏈
   - 明確指出問題位置：`action[%d].filters[%d]`
